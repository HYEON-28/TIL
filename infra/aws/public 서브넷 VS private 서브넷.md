# public 서브넷 VS private 서브넷

md-blog프로젝트의 인프라 설정에서 ALB만 public 서브넷에 두고,
나머지 서비스들(Fargate, RDS, Redis) 은 모두 private 서브넷에 두는것이 권장되었다.

public서브넷에 두고 방화벽 관리를 잘 하면 되지않을까 싶어서 이유를 찾아보았다.

## Public 서브넷에 놓으면

- 리소스에 공인 IP가 할당됨
- 인터넷에 IP 자체가 노출 → 보안그룹 설정 실수 한 번에 DB 직접 노출
- 포트스캔, 브루트포스 시도가 상시 들어옴

## Private 서브넷에 놓으면

- 공인 IP 자체가 없음
- IP가 인터넷에 존재하지 않으니 공격 시도 자체가 불가능
- 보안그룹 설정을 실수해도 뚫릴 경로가 없음

```
Public + 보안그룹 → 문에 자물쇠를 채운 것
Private → 문이 아예 없는 것 (외부에서 존재 자체를 모름)
```

---

- 실무에서는 "설정 실수의 영향 반경을 줄이는 것"이 핵심이다. 실수로 보안그룹 설정을 잘못해도, Private 서브넷에 있는 경우 인터넷에서 접근자체가 안된다.
- 하지만 초기 개발단계에서는 비용과 복잡도를 줄이기 위해 Public에 다 넣고 보안그룹으로 관리하기도 한다.

## public 서브넷과 private 서브넷 구분하는법

- 라우팅 테이블 확인하기
  목적지 대상
  10.0.0.0/16 → local ← 이것만 있으면 Private
  0.0.0.0/0 → igw-xxxxxxxx ← 이게 있으면 Public
  0.0.0.0/0 → nat-xxxxxxxx ← 이게 있으면 Private (NAT 경유)

* (172.31.0.0/16: AWS 기본 VPC이며 다 public subnet으로 설정되어 있어서 사용하지 않는것이 관례임)
